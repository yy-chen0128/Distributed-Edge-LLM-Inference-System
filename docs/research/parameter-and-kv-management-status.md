## 1. 先把名词定义清楚

### 1.1 token / prefill / decode

- **token**：模型处理文本的最小单位。文本先被切成 token，每个 token 对应一个整数编号。
- **prefill（预填充）**：把整段提示词（prompt）一次性喂进模型，为每个 token 算出内部表示。这一步是"批量并行"的——N 个 token 一起算，所以吞吐高。
- **decode（逐字生成）**：之后每生成**一个** token 都要把所有层再过一遍。这一步每次只算 1 个 token，所以**每次都要把这一层的全部权重从显存读一遍**。
- 结论：prefill 是"算力型"，decode 是"读带宽型"。这就是为什么长 prompt 的负载和长输出的负载是两种完全不同的负载。

### 1.2 KV 缓存：为什么存在、有多大

生成第 k 个 token 时，注意力需要看到前面所有 token 的 Key/Value。如果每次都重算，代价是 O(k²)。所以模型把每个 token 在**每一层**算出的 Key/Value 存下来，下次直接用——这就是 **KV 缓存**。

- 它是**每个请求私有**的（不同请求的历史不同），随上下文长度**线性增长**。
- 我们的实测（0.5B，6 层，38 token）：**116,736 字节 = 0.117 MB**；每多一个 token 增加 3,072 字节（= 每层 512 字节 × 6 层）。
- 公式：`每 token 字节 = 2(K和V) × KV头数 × 头维度 × 精度字节 × 层数`
  - Qwen2.5-0.5B：2×2×64×2×24 = 12.3 KB/token → 4k 上下文 50 MB
  - Qwen2.5-7B：2×4×128×2×28 = **56 KB/token** → 4k 上下文 **0.23 GB**，32k 上下文 **1.8 GB**
- 所以 KV 是切层时必须进的预算项，尤其在长上下文时。

### 1.3 层、分层流水线、每层权重

- 一个大模型由若干**结构相同的层**串起来（Qwen2.5-7B 有 28 层）。
- **分层流水线（PP）**：把第 0–6 层放 A 机、7–13 层放 B 机……A 算完把中间结果（activation）发给 B，B 接着算。这样一台机器只需要装自己那几层。
- **每层权重**（实测/按 config 算）：0.5B 是 **29.8 MB/层**；7B 是 **466 MB/层**（fp16）。
  注意 7B 的注意力用了 GQA（28 个 query 头但只有 4 个 KV 头），所以每层比我早先口头估的 510 MB 小。

### 1.4 词表、embedding、lm_head

- **词表（vocabulary）**：模型认识的所有 token 的集合，Qwen2.5-7B 有 **152,064** 个。它本身不是一个"表"，而是**两个大矩阵**：
  - **embedding**（第一层）：`[词表大小 × 隐藏维度]`，把 token 编号变成向量。7B：152064×3584 → fp16 **1.09 GB**。
  - **lm_head**（最后一层）：`[隐藏维度 × 词表大小]`，把内部向量变成"下一个 token 是每个词的概率"。7B：同样 **1.09 GB**。
- 这两个矩阵**只出现在首段和末段**。当模型不共享词表（`tie_word_embeddings: false`，Qwen2.5-**7B/14B 是这种**）时，首段和末段各背一份 = **2.18 GB**，占整个 7B 模型的 14%。
- 这就是"词表切分"这个议题的来源，见 §8。

### 1.5 progress_tokens（你问的那个）

**定义**：一个整数，记录"这个请求**已经生成到第几个 token**"。
比如一个请求要生成 200 个 token，在第 150 个时机器被抱走了，那么中断那一刻它的 `progress_tokens = 150`。

它就是"**这个请求的进度条读数**"。

## 2. progress_tokens：用途、bug 到底是什么

### 2.1 为什么要有它

因为它决定"中断之后要从头再来多少"。

一个请求的工作量 = **prefill 整段提示词** + **逐个生成 T 个 token**。中断后：

| 有没有进度信息 | 恢复时要重做的事 |
|---|---|
| **没有**（progress=0） | 重新 prefill 提示词 + 重新生成那 150 个 token |
| **有**（progress=150） | 理想情况只推进 1 步 |

用我们实测的每层常数（§表 §0）粗算 7B + 7.6K 提示词（Mooncake 的平均值）+ 已生成 150 token：

| 重做项 | 估算 |
|---|---|
| 重新 prefill 7.6K token | 28 层 × 0.0334 ms/token/层 × 7600 ≈ **7.1 s** |
| 重新生成 150 token | 150 × (28 层 × (0.99 固定 + 0.033 边际)) ≈ **4.3 s** |
| 合计白扔 | **≈ 11.4 s** |

（这两个数是**按实测每层常数向 7B 外推的估算**，不是实测；但量级说明问题：长提示词 + 长输出时，中断一次的浪费是十几秒级。）

### 2.2 它现在为什么没用：三个部件各在一处

要让它生效，需要**三个东西同时存在**，而它们现在分散在三个地方：

| 需要的东西 | 通俗说 | 现在在哪 | 状态 |
|---|---|---|---|
| 知道"生成到第几" | 进度条的读数从哪来 | 逐 token 生成的**循环**在 `run_real_pipeline.py`（实验驱动）里 | 有循环，但它在**调度器之外**，那里**没有恢复逻辑** |
| 中断后决定怎么重跑 | 看到进度条读数后怎么办 | `TaskScheduler._on_node_left`（调度器） | 有恢复逻辑，但**拿不到进度读数** |
| 前缀的 KV 本身 | 恢复时"接着算"要用的原料 | agent 进程里的 `DynamicCache`（按 `epoch+request` 隔离） | 有，但**没有导出/导入接口**，跨进程搬不走 |

### 2.3 于是 bug 是两个洞（不是一个）

**洞 1（进度永远是 0）**：全仓库搜索 `progress_tokens` 只有四处——类型定义、恢复策略里的搬运、引擎里的读取、一个测试。**没有任何代码给它赋值**。
原因就是上面第一行：真正逐 token 生成的循环不在调度器里，而调度器是唯一会处理中断的地方。
后果：`TokenRecovery`（token 级恢复）恢复出来的任务永远带 `progress_tokens = 0`，行为**和"从头重跑"完全一样**——这个策略实际上从没生效过。

**洞 2（就算进度写对了，KV 也不在）**：节点离开意味着**那台机器不在了**。要"接着算"，恢复的目标机器必须已经拥有这段前缀的 KV。而这需要"把 KV 搬过去 + 装进目标机器的 cache"——这条能力**完全没有**（见 §4.4）。
更糟的是原实现遇到这种情况会**静默算错**：它看到 `progress_tokens > 0` 就只喂最后一个 token，而目标机器的 cache 是空的 → 模型看到的是一个"只有一个 token 的序列" → 输出是垃圾但不报错。

> **我本轮修掉的是洞 2 里最危险的那一半**：cache 不在时，不再假装能续算，而是**退回整段重算**（慢，但结果正确），并打日志。
> **洞 1 我没修**，因为修它要动解码循环的归属（见 2.4）——这是架构决定，不该我顺手改。

### 2.4 为什么修它"要动调度器之外的东西"

因为**"逐 token 生成"这件事现在根本不在调度器里**。调度器的一次调用是这样：

```
收到请求 → 决定路由 → 让每段各算一次 → 返回（只产出 1 个 token）
```

它**没有 `for step in range(max_tokens)` 这个循环**。所以调度器里不存在"第几步"这个概念。

最小修法分两步：

1. **P0（约半天，纯接线）**：把逐 token 的循环搬进调度器。每生成一个 token，就把这个 token 追加到该请求的序列上、并把 `progress_tokens += 1`。
   → 效果：**同节点中断恢复**立刻变成真的能省算（那台机器的 cache 还在）。
2. **P1（约 2–3 天）**：给引擎加"导出 KV / 导入 KV"两个操作，走已有的 TCP 通道把 KV 搬到新机器。
   → 效果：**跨节点恢复**才成立。这同时就是"真实 KV 迁移"本身。

第 1 步不需要任何新技术，只是把已有代码挪个位置；第 2 步是真正的工作量。

## 2.5 位置读数从哪来（三种来源）

"识别进行到什么位置"**不需要读 KV 张量**，有三条路，优先级如下：

| 来源 | 怎么做 | 可靠性 |
|---|---|---|
| **① 控制面自己数**（最可靠） | 控制面发起了这个请求，它收到了几个 token 它是知道的（prompt 长度 + 已生成数）。**这也是唯一在设备被抱走/断电时仍然可用的来源** | ✅ 推荐作为权威 |
| **② 引擎自报**（已实现，本轮加的） | 引擎知道每个请求的 cache 里有多少个 token。实测：38-token prefill 后报 38，4 次 decode 后报 43；两个请求各自独立（`{'req-A': 43, 'req-B': 10}`） | ✅ 但**只有活着的进程**能回答；优雅退出时可上报 |
| ③ 从 KV 字节数反推 | KV 字节数 ∝ 位置（每 token 固定增量） | ⚠️ 可行但没必要——② 直接给位置，③ 还要先知道每 token 字节 |

**你问的"能不能通过读 KV 缓存识别"——能，而且比读 KV 更简单：让 cache 报自己的长度就行。**
实测增量是线性的：0.5B 每 token +3072 字节（6 层），位置 38→43 对应字节 116,736→132,096。

**你问的"设备主动断开时可以自己记录"——对，而且这是最值得做的那条**：优雅退出（用户点了关机、进程收到信号）
时把"我持有这些请求、各自进度是多少"上报给控制面。缺的是这个**上报动作**（协议 + 退出钩子），
不是读数能力。被抱走/断电时问不到，所以 ① 必须作为权威来源。

## 2.6 中断恢复：新机器到底需要什么（activation 够不够？）

**先回顾数据流**。4 段流水线，段0 装层 0–11、段1 装 12–15……生成第 p 个 token 时：

```
段0 吃 token_p           → 算出 h_p^(12)（第 12 层的输入）→ 发给段1
段1 吃 h_p^(12)          → 算出 h_p^(16)                  → 发给段2
段2 → 段3（末段，含输出头）→ 采样出 token_{p+1}            → 交回段0
```

**关键点：一次 activation 只够推进"当前这一步"。** 假设段1 的机器在中途没了：

- 如果只知道"段0 给段1 的那份 activation"，段1' 能算出**第 p 步**的输出；
- 但第 p+1 步时，段1' 必须对**前面所有 token** 做注意力——那是**累积的历史**，不在 activation 里。
- 所以 **activation 不够**：它是一次性的输入，KV 才是历史。

**新机器需要三样东西：**

| 需要什么 | 是否要"迁移" | 说明 |
|---|---|---|
| **它那几层的权重** | ❌ **不需要迁移** | 静态资产：任何机器都能从磁盘装同一份（这就是"模型参数不必搬"的原因） |
| **该请求在它那几层的 KV（位置 0..p）** | ✅ **要**（或重算） | 唯一真正需要搬的请求相关状态 |
| **位置读数** | ✅ 要，但很小 | 控制面存着（§2.5 ①） |
| 当前这一步的 activation | ❌ 不用搬 | 上游可以用自己的 KV **廉价再生**（一次单 token forward，7.2 kB） |

**"搬 KV" vs "重算" 的量化对比**（7B、hidden 3584、bf16、WiFi 40 MB/s；用实测每层每 token 0.0334 ms 外推）

| 恢复方式 | 传输量 | 阻塞时间 | 上游要配合吗 |
|---|---|---|---|
| **搬 KV** | `2048 B × L段 × p`（段1 在 p=4096 时约 33.6 MB） | 传输时间 ≈ 0.84 s | 否 |
| **重算** | 上游必须把 0..p 全部重跑，并传 p 份 activation（p=4096 时约 29 MB） | 上游 `p × L上游 × 0.0334 ms` + 本段同量 ≈ 3.3 s | **是**（上游必须还活着且有空） |

→ **除首段之外，一律"搬 KV"**：传输量相当，但阻塞时间差 4 倍，而且不需要上游配合。
→ **首段是例外**：它没有上游，可以**自己拿原始 token 序列重算**（控制面存着 prompt + 已生成 token）。
   p=4096 时自算约 1.6 s，而搬它自己的 KV 要 100 MB ≈ 2.5 s → **首段自算更划算**。

**所以"迁移"在我们系统里的准确含义**：把**请求的 KV**（按层、按 token 区间）搬到另一台机器。
模型参数是静态资产；activation 可以再生；位置信息是控制面的一行账。

> 这也说明为什么 §4.4 那座"引擎 ↔ 存储"的桥是关键路径：它决定了"搬 KV"这条路能不能走通。
> 走不通时，退路是"重算"（正确但慢 4 倍且要求上游存活），两条路都不通就只能丢请求。

## 3. 参数管理：现状

**已实现**

- 用 `torch.device("meta")` 建一个"只有骨架、不占内存"的模型，再**只把自己那几层的权重**从 safetensors 读进显存。
- 实测（0.5B，bf16）：6 层驻留 **451.2 MB**（其中首段额外背 **272.3 MB** 词表）；24 层 **988.1 MB**；**29.8 MB/层**（用两个尺寸差分得到，抵消了词表）。
- 节点变化时会重新算切分、重新装载（`prepare_epoch` → `activate_epoch`），旧配置要等新配置就绪才退役。

**没有实现**

- **参数换出/换入**（offload）：没有"把暂时不用的层挪到内存/盘、要用时挪回来"的能力。所以我们**不能**在同一台机器上放超过显存的模型，只能靠"少放几层"。
- **量化**：只会读标准 fp16/bf16 权重（详见 `real-workload-datasets.md` §7.3：AWQ/GPTQ 会被静默忽略）。
- **跨进程共享**：4 个 agent 进程 = 4 个独立的 CUDA 上下文，同一个词表在首段那边各占一份。
- **释放策略**：只有 `retire_epoch`（换 epoch 时）会释放，没有 LRU/按需换出。

## 4. KV 管理：现状

### 4.1 已实现

| 能力 | 说明 |
|---|---|
| 按请求隔离存储 | 每个 `(配置版本, 请求)` 一份 KV，互不干扰 |
| 释放 | 请求结束调 `release_request`，实测 KV 归 0 |
| 计量 | `kv_bytes(请求)` 返回字节数；`status()` 会按请求列出 |
| 配置版本隔离 | KV 的键带 epoch，跨版本混用会被引擎直接拒绝（抛错，不是静默算错） |
| 块级抽象与索引 | `KVBlock`（含 `block_hash`/`num_tokens`/`layer_range`/`reuse_count`/`prefill_time_ms`）+ `KVStore` 的 `save/load/move/evict/lookup/get_index/estimate_move_cost` |
| 两种存储后端 | `MockKVStore`（内存字典，用于仿真）与 `LMCacheStore`（包真实 LMCache） |
| 迁移的决策与执行 | `PriorityMigration`：按 `复用次数×重算耗时` 降序，在 deadline 预算内搬，超预算的丢弃 |

### 4.2 计量曾经是坏的（本轮修复）

四机运行里每个 stage 都上报"KV = 0"，看起来像"根本没存 KV"。实测查明是**计量读错了 API**：transformers 5.x 的 cache 对象不再支持 `cache[i]` 下标访问，抛出的异常被 `except ... continue` 吞掉 → 恒返回 0。
真实位置是 `cache.layers[i].keys/.values`。修完实测：**116,736 字节**（38 token、6 层，与公式逐字节吻合），每步 +3072，释放归 0；四段流水线合计 **0.47 MB**。

顺带一条给以后定规矩：**不能用"显存增量"当 KV 计量**——同一次调用的显存增量是 8.64 MB，是真实 KV 的 **74 倍**（前向中间张量 + 分配器池），而且释放请求后**不降**。

### 4.3 "命中"目前只影响路由，不影响计算

`E2Placement` 会查 KV 索引，判断"这个请求的前缀是不是某台机器上已有"，从而把请求路由到那台机器。但**引擎没有"把已有的 KV 装进 cache、然后跳过 prefill"的接口**。所以：

> 现在的"缓存命中"省的是**决策**，不是**计算**。它让请求去了对的地方，但到了那里仍然从头算。

这是与"KV 复用"这个卖点最不匹配的地方，也是 `KV 注入` 这一行标 ❌ 的含义。

### 4.4 迁移能力缺一座桥

`PriorityMigration` 那套（§4.1 最后两行）搬的是 **`KVStore` 里的"块对象"**。而真实的 KV 是引擎里按序列连续存放的张量。两者之间**没有转换代码**：

- 引擎算完一次前向，返回的 `kv_block_ids` 是**空列表**（HF 引擎不产出块），所以真实运行时 `KVStore` 里**始终是空的**；
- 于是迁移策略在真实部署里没有东西可搬，只在仿真（`MockKVStore`）里有意义。

要打通需要三样东西：
1. **导出**：把某请求在某一层的 KV 张量按"层 + token 区间"取出来（这是"按层可寻址"，不是完整分页）；
2. **装回**：在目标机器上把张量写进 cache 的正确位置（注意：我们把 `layer_idx` 改成了**本段局部索引**，导入时要按目标段的全局层区间再映射一次）；
3. **搬运**：走已有的 TCP 通道；顺带把"跨机 vs 本机"的成本差异喂给迁移决策（成本模型已经改成含链路的，见策略文档 §7）。

## 5. KV 迁移与价值评估：该有的两块，各自怎么来

你问"我们应该有的是对 KV 移动的操作能力（借助 LMCache 的接口），以及对 KV 价值的评估？"——**这个拆法是对的**，对应关系是：

| 你指的能力 | 现状 | 该怎么补 |
|---|---|---|
| **移动** | 只有"块抽象"层的 `move`，没有真实张量的搬运 | 借 LMCache 的**层粒度原语**。我们之前查过：LMCache 的上层 API（`store_layer/retrieve_layer/lookup`）要求"全层命中"，不适合分层流水线；正确用法是绕开它，直接用 `storage_manager` 的 key 级原语（`batched_allocate/batched_put/batched_get/batched_contains/batched_remove/pin`），层区间就是我们自选的 key 子集。**但即使有 LMCache，仍需要"引擎 ↔ LMCache"的桥**（把 GPU 张量按层导出成 LMCache 的 K/V，以及反向导入）——这就是 §4.4 那三样。 |
| **价值评估** | 公式（`复用次数 × 重算耗时`）和排序都有，且已修掉"复用次数为 0 就恒为 0 分"的问题 | **缺的是输入**：`复用次数` 和 `重算耗时` 在真实运行里从没被统计过。这两项**不需要 GPU 就能先做**：用真实数据集离线算（Mooncake 的轨迹直接给 512-token 前缀块哈希，可以统计"每个块被多少个请求共享"；重算耗时用实测的每层每 token 常数 × 块长）。**这是下一步性价比最高的一件事。** |

## 6. 分页/块管理：要不要自己做？

**先定义**：分页（PagedAttention）是把每个序列的 KV 切成固定大小的小块，另用一张表记录"逻辑块 → 物理块"。它解决三件事：显存碎片、不同长度序列的混合、同机内多序列共享前缀。

**vLLM 有，但我们继承不到**——因为我们的 stage 运行时是自己写的 HF 引擎，用的是 HF 的**连续 cache**，不是 vLLM 的引擎。

**我们需不需要**：需要区分两件事——

| 需求 | 分页能提供吗 |
|---|---|
| 同机多序列的显存碎片管理 | 能，但**我们的并发规模小**（单机 4 个 agent、每 agent 一个 stage），碎片不是主要矛盾 |
| **跨机、按层/块地搬 KV 并评估价值** | 分页**不直接提供**；需要的是"按层可寻址 + 导出/导入" |

**结论：不必自己实现完整的分页分配器。** 需要的是 §4.4 那座桥。
两条路线，各有代价：

- **A. 继续自研引擎**：自己写"按层导出/导入"（2–3 天，完全可控，保住了异构切层与弹性）。
- **B. 换 vLLM 当 stage 引擎**：分页、连续批处理、前缀缓存**白拿**，而且 vLLM 的 KV connector 层粒度接口（`save_kv_layer(layer_name)` / `wait_for_layer_load(layer_name)`）正好就是"按层可寻址"。
  **代价**：vLLM 的流水线并行是**同构静态**的（每段层数相同、节点集合固定），**不支持异构切层和节点离开**——而那正是我们这个项目要证明的东西。选 B 等于把差异点让掉。
  （我们之前评估过：vLLM 的免 fork 扩展面里**没有**"运行时改 PP 切分"的接口，所以选 B 要么放弃弹性，要么 fork。）

## 7. 专家（MoE）分层卸载：只有字段，没有代码

**概念**：MoE 模型里每层有多个"专家"（小的前馈子网络），每个 token 只激活其中少数几个。因此可以让**热门专家常驻显存、冷门专家放内存**，按需换入换出。

**我们的现状**：

| 层 | 有什么 |
|---|---|
| 数据结构 | `ModelPlacement.experts_gpu` / `experts_cpu`、`NodeState.expert_ids` / `expert_ids_cpu`、`ModelSpec.experts`、`ExpertSpec` —— **字段都留好了** |
| 代码 | **没有任何装载、卸载、换入换出的实现**；也没有任何 MoE 模型的实测 |

**我建议先不做**，理由：

1. 四台消费级笔记本的**显存总量只有 22 GB**，MoE 的收益来自"专家总量远超单机显存"，而我们的瓶颈在带宽（专家换入换出要走 PCIe/网络）；
2. 会把"专家命中率"这一整套新变量引进来，而我们现在连 dense 模型的四机分层都还没实测跑过；
3. dense 7B 的四机分层 + 弹性，已经能把"异构 + 节点会走"这个故事讲完整。

**如果要做，最小形态**是"冷专家放 CPU 内存"（不跨机），单机就能验证，代价最小。

## 8. 词表切分：为什么会有这个东西

### 8.1 为什么占显存

见 §1.4：首段要装 **embedding**、末段要装 **lm_head**，7B 各是 **1.09 GB**。
Qwen2.5-7B 的 `tie_word_embeddings = false`（可从下载下来的 `config.json` 直接看到）→ **两份都要装，共 2.18 GB**。

**问题在于它们落在哪两台机器上**：如果首段或末段正好落在 4 GB 的机器上，光词表就占掉 1.09 GB，那台机器就几乎放不下几层了。

### 8.2 "词表切分"到底指什么

指**把词表这个矩阵也切开、分散到多台机器上**，而不是整份放在首段/末段。这是"在词表维度上做张量并行"：

- 首段：查表需要跨机通信（拿到的 embedding 行在其他机器上）；
- 末段：算"下一个词的概率"需要把各机器算的部分拼起来再取最大值/采样。

**代价**：这是 **TP**（张量并行），而 TP 要求**每个 token 都要多机同步**。我们之前已经实测过结论：**跨 WiFi 做 TP 不可行**（每 token 需要几十次串行同步，单 token 延迟到几百毫秒级）。所以**真正的词表切分与我们的主线冲突，不该做。**

### 8.3 两个更省事的替代（推荐）

| 替代 | 做法 | 效果 |
|---|---|---|
| **① 把首/末段分给显存大的机器**（最省事） | 切层时把带词表的那两段固定给 8GB/6GB 的机器 | 零通信代价，纯调度问题。**我们的切层算法本来就有这个自由度**，只是现在它按算力分，没显式考虑"词表落在哪" |
| **② 词表用更低精度存** | embedding / lm_head 单独用 int8 存（减少一半） | 需要引擎支持混合精度；比 ① 麻烦，但能腾出 ~1 GB |

所以"词表切分 2–3 天"这个说法**要撤回**：正确做法是**切层时把词表当固定开销显式纳入约束**（①），而不是去做词表维度的并行。

## 9. 权重放哪：接受 `/mnt/d` 的代价（已决定）

实测：`/mnt/d`（Windows D 盘，通过 9p 挂载）冷读 **112.7 MiB/s**、热读 **114.5 MiB/s**（缓存不生效）；WSL 内部 ext4 **2319 MiB/s** —— **差 20 倍**。

- 你的判断对：**参数载入显存后运行时不读盘**，所以这是**一次性**开销。
- 但它发生在**每次节点集合变化**时（节点加入/离开/重新切层），所以它进入的是"**重配置延迟**"这个指标，而不是稳态吞吐。
- 已知代价：0.5B 每段 451 MB → 4.1 s（与实测 3.3–8.2 s 吻合）；**7B 最大一段 12 层 ≈ 5.6 GB → 约 52 s**。
- **决定（照你的意见）**：暂时放 D 盘。因为①它不是核心逻辑；②改动方便（换目录即可）；③C 盘的 vhdx 只增不减。
- **但要记住一件事**：等开始做弹性实验（节点反复进出）时，这 52 s 会直接变成实验里的"恢复时间"。到那时再决定是否把权重挪到 ext4、或给权重做一份 fp16/int4 的紧凑缓存。

## 10. 附录：7B 在四机上的实际算表（`scripts/model_pp_fit.py`，用真实 config 算）

Qwen2.5-7B-Instruct：28 层、hidden 3584、**4 个 KV 头**、head_dim 128、词表 152064、`tie=False`。
每层权重 **0.466 GB**（fp16）／**0.128 GB**（int4）；词表 **1.09 GB**；KV **56 KB/token**（4k 上下文 0.23 GB）。

**平均切（每段 7 层）在 8/6/4/4 上装不下**：

| 段 | 层数 | 权重 | 固定（词表/输出头） | 合计 | 预算 | 结果 |
|---|---|---|---|---|---|---|
| 0 | 7 | 3.26 GB | 1.09 GB | 4.35 GB | 8.0 | ok |
| 1 | 7 | 3.26 GB | — | 3.26 GB | 6.0 | ok |
| 2 | 7 | 3.26 GB | — | 3.26 GB | 4.0 | **OVER** |
| 3 | 7 | 3.26 GB | 1.09 GB | 4.35 GB | 4.0 | **OVER** |

（同一模型在 8/8/8/8 上平均切是装得下的——所以"平均切失败"是**异构**造成的，不是模型太大。）

**可行的加权切分**（留 0.8 GB 给 activation/上下文/碎片）：

| 方案 | 各段层数 | 各段合计 | 说明 |
|---|---|---|---|
| 按算力加权（12/4/4/8） | 12 / 4 / 4 / 8 | 6.68 / 1.86 / 1.86 / 4.82 GB | 早先部署文档算过可行 |
| 按显存均衡（8/6/6/8） | 8 / 6 / 6 / 8 | 4.82 / 2.80 / 2.80 / 4.82 GB | 词表放 6GB 机、输出头放 8GB 机，负载更平 |

**⚠️ 一个必须补的缺口**：我们的重切层算法（`CapabilityReparallelization`）**只按算力比例分层，完全不校验显存**。
在 8/6/4/4 上按算力比例直接分（例如 10/8/5/5），末段会变成 `5×0.466 + 1.09 = 3.42 GB > 3.2 GB` 可用预算 → **装不下，而且它不会报错，只会在装载时炸**。
所以上 7B 之前必须给该策略加一条"**显存可行性约束**"（每段的 `层数×每层字节 + 固定开销 ≤ 该机可用显存`），再在可行解里选最优。

### 10.1 实测：每层字节与分片对应关系（`scripts/probe_7b_split_map.py`）

直接读 4 个 safetensors 的文件头算出（不加载张量），7B 下载完成后实测：

- **每层 466.1 MB**（28 层完全一致；与 §1.3 推导的 466 MB 吻合）
- 非层张量：`embed_tokens` **1.1 GB**、`lm_head` **1.1 GB**、`norm` 7.2 kB
  （`tie_word_embeddings: false` → 两份都要装）
- HF 的 4 个分片：3.9 / 3.9 / 3.9 / 3.6 GB

**HF 分片边界与我们的层边界不对齐**，按 `12,4,4,8` 切时每段落在这些分片里：

| 段 | 层区间 | 权重 | 固定 | 合计 | 需要哪些 HF 分片 |
|---|---|---|---|---|---|
| 0 | [0,12) | 5.6 GB | embed 1.1 GB | **6.7 GB** | 分片 1 + 2 |
| 1 | [12,16) | 1.9 GB | — | **1.9 GB** | 分片 2 + 3 |
| 2 | [16,20) | 1.9 GB | — | **1.9 GB** | **只需分片 3** |
| 3 | [20,28) | 3.7 GB | lm_head 1.1 GB | **4.8 GB** | 分片 3 + 4 |

**两个部署结论**：

1. **每台机器不需要全部 15.2 GB**：按上面的对应关系，段2 只要 1 个分片（3.9 GB），段1 要 2 个（7.8 GB 文件，但实际只读 1.9 GB）。
2. **更好的做法是预打包成"每段一个文件"**（6.7 / 1.9 / 1.9 / 4.8 GB）：既能少传，又能让 `prepare_epoch` 顺序读、
   不必跨分片找层——结合 §3.8 实测的 `/mnt/d` 110 MiB/s，这一步直接缩短重配置时间。
