# 推理优化：我们的理解、要解决的问题与可能路径

> 这是一份**会议用总纲**：读完它应当能回答三件事——
> **① 大模型推理优化到底在优化什么（全貌）② 我们的系统要解决什么问题 ③ 有哪些可能的技术路径、各自代价。**
>
> 素材来源：本仓库的源码调研（vLLM / LMCache / 参考实现）与**本机实测**（RTX 4060 Laptop 8GB，
> 真实 Qwen2.5-0.5B、真实 GPU、真实 TCP），以及 `docs/research/`、`docs/deploy/` 下的专题文档。
> 文中每个数字都标注来源，未验证的结论显式标"未验证"。

---

## 0. 一页摘要

**我们做什么**：让**多个异构边缘设备协作执行一个大模型推理**——
把模型按层切成多段放到不同设备、跨机传激活、管理 KV 的驻留与迁移，
并在**节点中途加入/离开、链路波动、显存紧张**时继续服务。

**四个硬约束**（我们的场景与数据中心的根本差别）：
① 模型可能**装不下任何单台设备**；② 显存/内存紧；③ 节点间是 **WiFi/千兆**，比 NVLink 低 2–3 个数量级；
④ 节点**随时会走**（合盖、抱走、断网），且**没有宽限期**。

**三条已经有实测支撑的结论**（§3 有数据）：
1. **PP 不降低单请求延迟**，它买的是"装得下"和"吞吐"——所以论文里不能把 PP 说成加速手段；
2. **分段执行数值上无损**（4 段 vs 整体：token 全等、logits 逐位相同），
   所以**切分本身不引入误差**，误差只来自 dtype/实现；
3. **TP 在 WiFi 上不可行**（每 token 约 56 个串行同步点、约 280ms 纯等待），
   而 **PP 的 activation 极小**（7B decode 每 token 每边界仅 7KB）——这决定了我们的并行维度只能是 PP/EP。

**我们站在哪一层**：推理优化分五层（§1），我们在 **L4 集群与调度层**；
而 **vLLM 结构上不覆盖"分层跨机 × 节点离开缩容"这个组合**（`elastic EP` 与 `PP` 硬互斥），
这就是我们的立足点。

**当前进度**：控制面 + 数据面机制已在**单机多进程 + 真实 GPU**上跑通
（四段流水线、真实 KV、输出正确、`--local 4 --device cuda:0`）；下一步是四机与弹性实验。

## 1. 全貌：推理优化在五层里优化什么

同一个"优化"，在不同层解决的是完全不同的问题，**目标不同则机制不通用**。

| 层 | 优化对象 | 主要目标 | 代表手段 | 谁在做 |
|---|---|---|---|---|
| **L1 模型与算法** | 权重、KV、解码过程本身 | 精度-成本权衡 | 量化(INT4/FP8)、剪枝、蒸馏、**KV 压缩/驱逐**、低秩 KV(MLA)、**投机解码**、MoE 稀疏化 | 模型团队、算法研究 |
| **L2 算子与内核** | 单步计算怎么在硬件上跑完 | 单步延迟/带宽 | FlashAttention 2/3/4、PagedAttention、融合算子、**自定义 mask（FlexAttention）**、CUDA graph | 引擎/内核团队 |
| **L3 引擎与执行** | 单实例怎么组织请求与 KV | 吞吐/TTFT/显存 | **连续批处理**、chunked prefill、**前缀缓存**、KV 分层 offload、抢占、投机解码集成 | vLLM / SGLang / TRT-LLM |
| **L4 集群与调度** ★ | 多机之间怎么放、怎么走、怎么变 | 容量/吞吐/成本/**鲁棒性** | 并行策略搜索、**跨机切层**、请求路由、**PD 分离**、**弹性再并行化**、**KV 跨机迁移**、专家放置 | **我们**、Helix/SpotServe 等 |
| **L5 基础设施** | 互联、存储、功耗 | 成本/能效 | NVLink/RDMA、权重流式加载、资源池化、DVFS | 硬件/云厂商 |

**关键判断（决定了我们该往哪投）**：
- **L1/L2 的成果是"可用组件"，不是我们的战场**：量化格式、attention kernel 需要内核团队与硬件耦合，
  我们的消费级卡还受架构门槛限制（FA3 需 Hopper；sm86 上 FP8 基本不可用）。
- **L3 是"必须会用、但不必重写"的层**：连续批处理/前缀缓存直接复用 vLLM；
  但 L3 的 KV 管理只到"单实例 + 节点内分层"，**跨节点是空白**。
- **L4 是我们唯一有结构性优势的层**：因为我们的硬件能真实制造那四个约束。

## 2. 我们的系统要解决什么问题

### 2.1 四个硬约束（每个都附量级）

| 约束 | 具体表现 | 我们实测/估算的量级 |
|---|---|---|
| **装不下** | 7B fp16 需 15.2GB 权重；单台 8GB 卡装不下（更别说 4GB 卡） | `model_pp_fit.py` 实测每层 0.466GB、词表 1.09GB |
| **显存紧** | KV 随上下文线性增长；4k 上下文 7B 需 0.23GB，14B 需 0.79GB | 同上；`cache_dtype`/按层跳过量化可缓解 |
| **链路慢** | WiFi/千兆 vs NVLink：低 2–3 个数量级 | 本机 loopback 165MB/s、RTT 0.14ms（**真实 WiFi 待同学测**） |
| **节点会走** | 合盖/抱走/断网即离线；无 30s 宽限期 | 实测重切 4→3 节点耗时 2.15s、旧 epoch drain 0.76s |

### 2.2 六个子问题（研究问题清单）

| 编号 | 问题 |
|---|---|
| **D1 任务拆分** | 把推理任务拆成可调度阶段：按层、按专家、按 prefill/decode |
| **D2 协作执行** | 多设备如何协同完成**同一个**请求（而不是各跑一份完整模型） |
| **D3 分配/调度** | 按算力、显存、队列、KV 命中、链路状态分配任务 |
| **D4 离开/加入** | 中途离开/加入时的装载、卸载、状态迁移与恢复 |
| **D5 新单元评估** | 新设备到来时如何评估能力、决定它承担多少 |
| **D6 非数据中心通信** | 弱网/不稳定链路下的通信与切分协同 |

### 2.3 与数据中心场景的差别（为什么现成系统不够用）

| 维度 | 数据中心 | 我们 |
|---|---|---|
| 设备 | 同构、同代、同型号 | **异构**（不同型号/显存/算力，甚至含 CPU 节点） |
| 互联 | NVLink/InfiniBand | **WiFi / 千兆**，带宽与延迟都差 2–3 个数量级 |
| 节点生命周期 | 长稳、有宽限期、可预占 | **随时离开、无宽限期**、还会降频过热 |
| 模型放置 | 静态并行配置、一次性启动 | 需要**运行中重切**与**状态迁移** |
| 优化目标 | 吞吐/成本（延迟次之） | **能跑起来 + 不中断 + 吞吐**，单请求延迟不是首要 |

### 2.4 一个具体的目标场景（把问题落地）

> 4 台消费级笔记本（8+6+4+4GB），要跑 **Qwen2.5-7B fp16**（单机装不下）：
> - **切层**：首段 12 层（8GB 机，含 embedding）、中间 4+4 层（4GB 机）、末段 8 层（6GB 机，含 lm_head）；
> - **执行**：请求逐段流过，段间只传 hidden states（prefill 68KB、decode 1.8KB/token）；
> - **弹性**：某台机器被合盖 → 剩余 3 台重切 → 新请求走新 epoch，旧 epoch 排空后释放；
> - **迁移**：离开节点上的 KV 按价值（重算代价 × 复用度）与时间预算**部分抢救**，其余重算。

## 3. 我们已经确立的结论（含实测数字）

> 全部来自本机实测或源码核实；这是后面"选路径"的事实基础。

### 3.1 分段执行数值无损 ✅
4 段切分 vs 整体执行：**生成 token 完全相同，每一步 logits 最大绝对差 = 0.0**。
→ 后续所有差异都只能来自 dtype（如 fp16 传输）或实现，**不来自切分本身**。

### 3.2 PP 改的是容量与吞吐，不是单请求延迟 ⚠️（重要）
同机同线程数（6 线程）：单机整模型 **decode 128.5 ms/token**；4 段流水线 **147.5 ms/token（慢 15%）**。
原因：流水线逐 token 延迟 = Σ各段计算 + Σ跨段通信，而各段之和就是整模型的计算量。
→ **论文表述必须写"装得下 + 吞吐扩展"，不能写"加速单请求"**（单请求加速只有 TP/量化那条路）。

### 3.3 两端有固定开销 ⇒ 平均切会失败，能力加权切能成功 ⚠️（可直接做实验）
7B fp16 在 8/6/4/4GB 上：
- 平均切 7/7/7/7 → 4GB 机需 3.49GB > 3.2GB 预算 → **装不下**；
- 加权切 **12/4/4/8** → 全部通过（首段背 embedding 1.09GB、末段背 lm_head 1.09GB）；
- **且最优切分对显存不单调**：末段要额外背输出头 → **把末段放到显存更大的机器上反而更优**。
→ 切层求解器必须显式建模"两端固定开销"（`CapabilityReparallelization` 的第一个真实用例）。

### 3.4 跨段 activation 极小 ⇒ 弱网可行 ✅
0.5B：prefill 68KB/hop（fp16）、decode 1.8KB/token/hop；7B decode 约 **7KB/token/边界**。
→ 即使 1MB/s 的链路，7KB 也只占 7ms，**PP 的通信不是瓶颈**（与 TP 形成鲜明对比）。

### 3.5 TP 在 WiFi 上不可行 ❌（定量）
7B、2 路 TP、28 层：每 token 通信量约 **200KB**、**约 56 个串行同步点**；
WiFi RTT 5ms ⇒ **≈280ms/token 的纯等待**（对比 PP 的 21KB 与 3 个边界）。
→ 我们采用 PP/EP 的正当性**有定量依据**，不是"带宽不够"的定性说法。

### 3.6 重配置的成本主要在"装载"，不在协议 ✅
4→3 节点重切总耗时 **2.15s**，其中协议/drain 仅 **0.76s**；初始 4 节点 prepare+activate 8.67s。
→ 优化点在 **权重装载/缓存/量化**，也是"节点加入要多久才能干活"的决定因素。

### 3.7 并发只有 1.55× ⇒ 缺"批处理与重叠" ⚠️
K=1→2→4：吞吐 5.06 → 6.54 → 7.82 tok/s（**1.55×**），且 agent 侧出现排队（`queue_ms` 达 357ms）。
原因：每个请求顺序走完全部段、每段一把锁——**单条流水线没被填满**。
→ 要区分两个概念：**"开几条流水线" = DP 副本数**；**"一条流水线里同时有多少批在飞" = 微批/并发批**。
   我们缺的是后者（vLLM 的 `ubatching` 就是干这个的）。

### 3.8 稀疏注意力分两类，只有免训练类我们能做 ⚠️
- **原生稀疏**（NSA/MoBA/DeepSeek-V4 sparse MLA）：pattern 是**训练出来的**，vLLM 的相关后端全是
  "model-driven"，且多数要求 SM90+/FP8 → 我们只能用别人的权重、且多半跑不动；
- **免训练稀疏**（自己定 mask / 按统计量挑 KV）：**可以做**，落点是 **FlexAttention**
  的 `mask_mod` + `block_sparsity_hint`（Triton，消费卡可用；**FA2/FA3 不支持 mask_mod，只有 FA4 支持**）。

### 3.9 "哪些 KV 参与计算"是我们真正的机会点 ⭐
在单机数据中心里这个旋钮只影响"计算量 + 显存"；在**跨机分层**场景里它**同时决定四件事**：
```
哪些 KV 参与计算
  ├─ 注意力计算量      （延迟）
  ├─ 本机显存占用      （能否开更长上下文）
  ├─ 节点离开时要迁移的字节  （恢复时间）
  └─ 前缀缓存可复用比例     （跨请求收益）
```
→ 差异化不在"再设计一个驱逐评分函数"，而在**这四效应的联合优化**（数据中心论文不关心后两项）。

### 3.10 已有系统的可复用边界（源码核实结论摘要）

| 系统 | 我们能**直接用**的 | 我们**必须自己做**的 |
|---|---|---|
| **vLLM** | 连续批处理+前缀缓存（=吞吐基线）、KV connector 的**逐层**钩子（`save_kv_layer(layer_name)`/`wait_for_layer_load`）、`kv_load_failure_policy=recompute\|fail`、量化、按层跳过 KV 量化、KV 分层 offload、EPLB 专家重排（含 NIXL 通信后端） | 运行中改 PP 拓扑、layer 级权重热插拔、把 PP activation 交给**外部**链路、跨节点专家常驻池 |
| **LMCache** | **存储层**（键含 `layer_id`、逐层 allocate/put/get）、分层压缩（CacheGen）、`lmcache_server` + `lm://` **纯 TCP 跨机字节通道** | 上层语义：它的 `lookup` 认死"**全层命中**"，`move` 不重映射 key，且**没有外部接口能注入 KV 张量**→ 只能当进程内嵌库；层区间语义要在 `LayerCacheEngineKey` 层重建 |
| **NVIDIA PAIR** | 请求级路由/信任/成员管理的**设计范式**（UUID 目录、资格门、驱逐防抖、预留、activity-as-liveness） | 它**不做**分层执行：不切模型、不共享 KV、不感知带宽 —— 与我们是**互补**关系 |

**一条结构性事实（我们的立足点）**：vLLM 的 `elastic EP`（节点增减）与 `PP`（分层跨机）**硬互斥**
（`config/parallel.py:846-850`），容错也只覆盖 DP/EP。
→ **"分层跨机 + 节点离开后缩容"这个组合，在原生 vLLM 里不可能同时成立。**

## 4. 可能的路径（8 条，每条回答四个问题）

> 每条格式：**要解决哪个约束 → 需要什么机制 → 我们已有什么/缺什么 → 与已有工作的差异与风险**。

### A. 请求级路由 / 数据并行（DP）
- **约束**：小模型（≤3B）每台都装得下时，如何把并发摊开。
- **机制**：每台跑完整模型 + 代理按负载/前缀命中路由（PAIR 范式、Preble 的 exploit/explore）。
- **已有/缺**：`E2Placement`、`CapabilityPlacement`、KV 目录；缺真实前缀命中与生产级代理。
- **差异与风险**：**红海**（PAIR/llm-d 已产品化）。价值在于当**基线**，不建议当主贡献。

### B. 跨机 PP + 能力加权切层 ★主线候选
- **约束**：装不下（模型 > 单机显存）。
- **机制**：按层切分、逐段流水、段间传 activation；切层求解器显式建模"两端固定开销 + 每层实测耗时"。
- **已有/缺**：★真实 HF 分层运行时、节点 agent、epoch 化重配置、链路测量、成本模型（§3.2/3.3）；
  缺 **微批/连续批处理**（把 1.55× 拉起来）、权重装载加速、**能力加权切层求解器**。
- **差异与风险**：Helix/EdgeShard 做过切层但假设固定集群；我们的增量是**异构 + 运行中重切 + 弱网**。
  风险：**PP 不降单请求延迟**（§3.2），必须把叙事放在容量与吞吐上。

### C. 弹性与状态迁移（KV + 权重）★主线候选
- **约束**：节点会走；且新增节点要尽快能干活。
- **机制**：离开时按价值/预算**部分迁移 KV**（或重算）；加入时**在线评估能力**并重切；权重可**P2P 从对端拉**。
- **已有/缺**：`PriorityMigration`（reuse×prefill_time + 时间预算）、`TokenRecovery`、epoch 蓝绿切流、
  `KVBlock.layer_range`；缺 **真实 KV 跨机迁移**、**P2P 权重分发**（vLLM 空白）、在线能力评估。
- **差异与风险**：SpotServe 依赖数据中心宽限期与同构 GPU；LoongServe 依赖 NVLink。
  **"弱网 + 异构 + 无宽限期"是空白**。风险：迁移可能比重算更贵（需要判据与消融）。

### D. MoE 专家放置与分级（EP 的边缘变体）
- **约束**：显存装不下稠密大模型，但装得下**部分专家**。
- **机制**：专家按热度分布在各设备，请求路由尽量对齐专家覆盖；未命中的专家走 CPU 分级或重算。
- **已有/缺**：`ModelManager.load_experts`（GPU/CPU 分级）、`NodeState.expert_ids`；
  缺可跑的 MoE stage runtime、专家级通信测量。
- **差异与风险**：EP 每层 all-to-all 是**逐层串行**同步，弱网下代价高（这正是可测的研究点）；
  vLLM 的 EP 是"同一实例内多 rank"，**跨节点常驻专家池不存在**。风险：收益可能被 all-to-all 吃掉。

### E. PD 分离 + 阶段异构放置
- **约束**：prefill 计算密集、decode 访存密集，两类机器性价比不同。
- **机制**：P 机与 D 机分开，KV 从 P 传到 D；与 PP 正交，可叠加。
- **已有/缺**：`NodeRole.PREFILL/DECODE` 接口、KV 目录；缺真实 KV 传输与 P/D 配比策略。
- **差异与风险**：DistServe/Splitwise 已在数据中心做完；我们做"**弱网 + 异构边缘**"的配比。
  vLLM 侧：NIXL push 的 producer 侧支持 PP>1，**decode 侧 PP>1 未实现** → 叠加需要自研。

### F. KV 稀疏/驱逐 × 迁移预算的联合优化 ★差异化候选
- **约束**：显存紧 + 链路慢 + 节点会走（三个约束同时）。
- **机制**：按 §3.9 的四效应统一决策——"不参与计算的 KV 也不用留、不用搬"。
- **已有/缺**：层粒度 KV 目录、迁移优先级；缺驱逐与迁移的**联合策略**、真实 KV 迁移实现。
- **差异与风险**：H2O/SnapKV 类方法已很密（**了解它们的现状是必须的，作为组件与 baseline**），
  但**没有工作把它与跨机迁移预算联合**。风险：需要先有（C）的真实迁移才能做联合实验。

### G. 量化 × 切层 × 调度的跨层协同
- **约束**：显存紧 + 算力弱。
- **机制**：量化不只是省显存——它**改变每层耗时与 activation 字节**，因此**改变最优切分点**。
- **已有/缺**：成本模型可复用；缺"把量化当调度输入"的建模。
- **差异与风险**：文献普遍把量化当**加速手段**，"量化改变调度决策"较少见。风险：需要实测多档量化的每层耗时。

### H. 能效/热约束调度（笔记本独有）
- **约束**：笔记本会降频/过热，功耗与温度是真实约束。
- **机制**：把功耗/温度/降频纳入放置与切层决策。
- **已有/缺**：什么都没有（新方向）。
- **差异与风险**：**数据中心论文不会碰这个**，是天然差异化；风险：测量设备与口径要自己搭。

### 4.9 路径汇总

| 路径 | 覆盖约束 | 依赖 | 验证难度 | 论文风险 |
|---|---|---|---|---|
| A 请求级路由 | 吞吐 | 无 | 低 | **高（红海）** |
| **B 跨机 PP + 加权切层** | 装不下、吞吐 | 微批 | 中 | 低（叙事要对） |
| **C 弹性与状态迁移** | 节点走、装入 | 真实迁移实现 | **中高** | **低（空白）** |
| D MoE 专家放置 | 显存、算力 | stage runtime | 高 | 中 |
| E PD 分离 | 异构性价比 | KV 传输 | 中 | 中（数据中心已做） |
| **F KV 稀疏×迁移预算** | 显存、链路、节点走 | C | 中高 | **低（联合是新点）** |
| G 量化×切层×调度 | 显存、算力 | 多档实测 | 低 | 中 |
| H 能效/热调度 | 降频/过热 | 测量装置 | 中 | **低（独有）** |

**建议的主线组合**：**B + C 为骨架**（先把"跨机跑起来 + 节点走了能继续"做实），
**F/G 作为差异化增量**，**A 作基线**，D/E/H 视人力选一到两条。

## 5. 与已有系统的关系：分工，而不是替代

| 系统 | 它解决什么 | 我们借什么 | 我们不重复什么 |
|---|---|---|---|
| **vLLM** | 单实例高吞吐服务（连续批处理/KV 分页/并行执行） | 基线引擎、KV connector 钩子、量化、EPLB | 不做"跨节点分层执行 + 弹性" |
| **LMCache** | KV 分层存储/压缩/复用 | 存储层与键方案、`lm://` 跨机通道 | 不做调度决策与层区间语义 |
| **SGLang** | 结构化生成、前缀缓存 | 对照基线 | 同上 |
| **NVIDIA PAIR** | 请求级路由、信任与成员 | 设计范式（目录/资格门/驱逐防抖） | 它不切模型、不共享 KV、不感知带宽 |
| **SpotServe** | 抢占实例上的动态再并行化 | 迁移与恢复的思路 | 它依赖宽限期与同构 GPU |
| **Helix** | 异构 GPU+网络的层切分与 max-flow 放置 | 建模思路（把网络当容量） | 它假设固定集群，不做运行中重切 |
| **MoE-Infinity / SMoE** | 专家 offload / 专家替换 | 专家分级与命中思路 | 我们不重复"单机专家缓存" |
| **Preble** | 前缀命中感知调度 | exploit/explore 的 E2 路由 | 不管分层与迁移 |

一句话：**它们都在 L1–L3 或 L4 的"部分格子"里，我们要补的是 L4 中"分层跨机 × 弹性"这一格。**

## 7. 待决问题（会议讨论）

1. **主线先做哪条**：B（把四机跨机 PP 跑通、加权切层）还是 C（先把弹性与真实迁移做实）？
2. **旗舰模型**：7B fp16（能演示"单机装不下 + 加权切成功"）还是 14B int4（更"大模型"但通信更重）？
3. **KV 路线**：走 vLLM 的自定义 connector，还是在自研 stage runtime 里自建 KV 层（借 LMCache 存储层）？
4. **要不要投 MoE（D）**：all-to-all 的弱网代价可能吃掉收益，但"边缘 EP"确实少人做。
5. **评测口径**：baseline 定成什么（单机整模型 / 静态平均切 / vLLM 完整 endpoint）？
   吞吐与延迟的 headline 数字用哪三个口径统一（见 `docs/research/` 与 `paper-evidence` 约定）？
6. **能效（H）是否作为差异化点**：笔记本降频是真实约束，但需要额外测量装置。

## 8. 术语表（面向新同学）

| 术语 | 含义 |
|---|---|
| **PP（流水线并行）** | 按**层**把模型切成多段，分到多设备，段间传激活；吞吐导向，**不降单请求延迟** |
| **TP（张量并行）** | 把**同一层**的权重矩阵切开并行算，需层内 all-reduce；**降延迟**但对互联要求极高 |
| **EP（专家并行）** | MoE 的专家分散到多设备，每层 dispatch/combine 两次 all-to-all |
| **CP/SP（上下文/序列并行）** | 按**序列**切分，用于长上下文 |
| **activation（激活）** | 段间传递的中间张量（hidden states）：prefill 是 `[seq, hidden]`，decode 是 `[1, hidden]` |
| **prefill / decode** | 处理整段 prompt（计算密集）/ 逐 token 自回归（访存密集） |
| **TTFT / TPOT** | 首 token 时间 / 每输出 token 时间 |
| **KV block** | KV 缓存的最小管理单位（分页），**带层区间** → 支持按层部分迁移 |
| **epoch（本项目）** | 一次完整的层放置计划版本；请求绑定 epoch，新旧并存、旧 epoch 排空后退役 |
| **churn** | 节点频繁加入/离开 |
| **gap / 宽限期** | 数据中心允许"节点即将被收回"的缓冲时间；**我们没有** |
| **DP** | 数据并行：复制整个模型，每副本处理不同请求（= 我们的"几条流水线"） |
| **micro-batch** | 把一批再切小，用来填流水线气泡、让通信与计算重叠 |
