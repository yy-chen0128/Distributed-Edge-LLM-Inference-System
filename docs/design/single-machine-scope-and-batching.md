# 单机范围与批处理/微批：先讲清楚再动手

> 这份文档回答两个问题：
> **(1) 只有一台机器（单机多进程）时，还能做什么有意义的工作？**
> **(2) 批处理 / 微批到底要做什么、能换来什么、要改哪里？**
>
> 是"动手前的说明"，不是实施承诺。所有数字取自本仓库已有产物（文件名与字段都标了出处），
> 其中有一处更正需要先看 §2.3。

---

## 1. 先把三个词分开（这是最容易混的地方）

系统记号：流水线有 $S$ 段（我们实测 $S=4$），第 $i$ 段处理一个请求、一个 token 的耗时记 $t_i$；
记 $t = \max_i t_i$（最慢段决定吞吐）。

| 概念 | 改的是哪个量 | 一句话 | 单机可行 | 不动模型权重 |
|---|---|---|---|---|
| **批处理**（batching） | 改 $t$ 的**构成** | 把 $K$ 个请求塞进**一次** forward，让一次调用的固定开销被 $K$ 个请求分摊 | ✅ 可以 | ✅ |
| **微批**（micro-batch / 流水线重叠） | 改**利用率** | 让 $S$ 段同时都有活干，消掉气泡；$t$ 不变 | ✅ 可以 | ✅ |
| **DP**（数据并行） | 改**并行度** | 复制整条流水线，多副本各自跑 | ✅ 可以（但单机没意义） | ✅ |
| **TP**（张量并行） | 改 $t$，但要**每层同步** | 一个矩阵乘拆到多卡 | ❌ 单机看不出，跨机不可行 | ✅ |

**关键区别（用我们自己的数据说）**：
DP 是"多修几条流水线"，微批是"让一条流水线别闲着"，批处理是"让每一段每次多干几个请求"。
**三者互相正交，可以叠加**，但动机完全不同：

- 单请求跑 4 段流水线时，稳态下**只有 1 段在工作**，另外 3 段空转——这是 PP 的固有气泡。
  微批就是往这条流水线里塞多个请求，把空转段填满。**这就是我们实测 K=1→4 吞吐上升的那件事**
  （`real_pipeline_conc.json`：5.06 → 6.54 → 7.82 tok/s）。
- 但微批只是**让段更忙**，每段每次仍然只处理**一个**请求的一个 token。
  如果"处理一个请求一次调用"的固定开销本身就远大于计算，那么段再满，吞吐也上不去——
  这就要靠批处理。**我们现在的数据表明，固定开销恰恰是大头（§2）。**

经典流水线的稳态利用率（$K$ 个在途请求、$S$ 段、每段 $t$）：

$$U = \frac{K}{K + S - 1},\qquad \text{吞吐} = \frac{K \cdot U}{t}\ \text{token/s}$$

$K=S=4$ 时 $U=4/7\approx0.57$；$K\to\infty$ 才趋近 1。**所以微批的天花板是 $1/t$，它消不掉 $t$ 里的固定开销。**

## 2. 为什么我们现在最该做的是批处理：把证据摆出来

### 2.1 GPU 实跑：每段的 hop 和 compute 一样大

`wsl_gpu_pipeline.json`（Qwen2.5-0.5B-Instruct，4 段 × 6 层，`wire_dtype=float16`）：

| 段 | prefill(38 tok) compute | prefill hop | decode(1 tok) compute 稳态 | decode hop 稳态 | activation |
|---|---|---|---|---|---|
| n0 | 946.9 ms | 1004.1 ms | 5.4 – 6.5 ms | 6.0 – 22.0 ms | 1792 B |
| n1 | 501.4 ms | 565.8 ms | 5.5 – 6.2 ms | 6.4 – 23.8 ms | 1792 B |
| n2 | 485.0 ms | 547.1 ms | 4.8 – 9.5 ms | 5.9 – 35.3 ms | 1792 B |
| n3 | 573.0 ms | 580.3 ms | 6.9 – 12.5 ms | 7.8 – 13.7 ms | 0 B |

（`ttft_ms = 2697`，`total_ms = 3302`，6 个 token。）

**两个观察，都很要紧：**

1. **hop ≈ compute**。而且我们的链路 RTT 实测只有 **0.141 ms**（`link_loopback.json`），
   1792 字节的 activation 在网络上花不了 1 ms。也就是说 hop 里的 **6–35 ms 有 97% 以上是进程内开销**
   （base64 + JSON 序列化、TCP 读写、asyncio 调度），不是链路。
2. **每段的固定开销和模型计算同量级**。

### 2.2 算一下 GPU 到底忙了多久（这个数字最刺眼）

Qwen2.5-0.5B 的 `hidden=896`、`intermediate=4864`、24 层，每层参数约 $4\cdot896^2 + 3\cdot896\cdot4864 \approx 1.63\times10^{7}$，
fp16 下**每层权重约 32.6 MB，6 层约 196 MB**。

| 指标 | 计算 | 实测 | 差距 |
|---|---|---|---|
| decode 6 层的**内存带宽下界** | 196 MB ÷ ~200 GB/s ≈ **1.0 ms** | 4.8 – 12.5 ms | 慢 **5–13×** |
| prefill 38 token 6 层的**算力需求** | $2\times1.63\times10^7\times38 \approx 1.24$ GFLOP | 0.49 – 0.95 s | **≈ 1.3–2.5 GFLOP/s** |
| 同上，占消费级 GPU（按 5 TFLOPS 计） | — | — | **≈ 0.03%** |

**结论：当前 stage 运行时的耗时几乎全部是框架开销，不是模型的算力或带宽需求。**
GPU 在 prefill 期间的有效利用率不到千分之一。所以"优化模型/算子"在这个阶段是错的方向，
**该优化的是"每次调用的固定成本"——那正是批处理要摊薄的东西。**

### 2.3 一处更正：1.55× 那组数字是 **CPU fp32**，不是 GPU

需要纠正一个容易被误读的地方：`real_pipeline_conc.json`（K=1/2/4 → 5.06 / 6.54 / 7.82 tok/s，1.55×）
里的 `device_kind` 是 **`cpu`**、`dtype` 是 **`torch.float32`**——**那是一次纯 CPU 运行**。
GPU 路径（`wsl_gpu_pipeline.json`）**目前只有单请求数据**，没有 K 扫描。

这不削弱它的价值，反而**强化**了上面的论断：
4 个 fp32 CPU 进程在一台 24 核机器上争抢，吞吐还能随并发上升 1.55×，
说明瓶颈确实是"每次调用只干一个请求"的串行化与固定开销，而不是算力。
它**不能**用来预测四机 GPU 的吞吐。

### 2.4 还有一个必须说清的边界：**四个 agent 现在共用同一块 GPU**

`wsl_gpu_pipeline.json` 里 n0/n1/n2/n3 的 `device` **全是 `cuda:0`**，`vram_total_bytes` 都是 8585216000。
也就是说我们所谓的"四段流水线"跑在**一张 8GB 卡上的四个进程**：四个 CUDA context、
四份显存碎片，谁也没有独占算力。

**这直接决定单机实验的边界**：

| | 单机能验证 | 单机**不能**证明 |
|---|---|---|
| 批处理 | ✅ 机制对不对、固定开销 $c_0$ 有多大、$T(K)$ 的形状 | ❌ 四机吞吐收益（GPU 是共享的，批越大越抢） |
| 微批 | ✅ 气泡与利用率（CPU 上已测过） | ❌ 四机稳态吞吐 |
| KV 迁移 | ✅ 正确性 + loopback 开销 | ❌ WiFi 下的真实代价 |
| 切层 | ✅ 算法行为 | ⚠️ 收益需真实异构（不同 GPU 型号） |

## 3. 单机具体能做什么（按性价比排序）

单机不是"只能等四机"，下面这些**现在就能做**，而且大部分不需要新硬件：

| # | 工作 | 目的 / 产出 | 成本 | 为什么单机够 |
|---|---|---|---|---|
| 1 | **测 $T(K)$ 曲线**（单进程、单段、GPU，$K=1,2,4,8,16$） | 拟合 $T(K)=c_0+c_1 K$，把"固定开销"和"边际成本"分开——**这是批处理收益的唯一诚实依据** | 半天，几乎不用改代码 | 只需要一个 stage 引擎和一个循环 |
| 2 | **单进程批处理原型** | 让一个 stage 一次处理 $K$ 个请求，验证数值正确性 + 拿到真实加速比 | 2–4 天（§4） | 不涉及跨机 |
| 3 | **KV 驱逐/选择原型** | 只让部分 KV 参与注意力（长上下文下的显存/带宽权衡） | 3–5 天 | 需要自定义 attention（FlexAttention mask），单卡可做 |
| 4 | **loopback 两进程真实 KV 迁移** | 把 KV 块在两进程间真搬一次：验正确性、量字节与耗时（接 `PriorityMigration`，现在它只有 mock 实现） | 2–3 天 | 不需要四机，loopback 即可暴露协议问题 |
| 5 | **量化档位 × 每层耗时表** | fp16 / int8 / int4 下的每层 compute 与 activation 字节 → 给"加权切层"喂真数据（现在喂的是 TFLOPS 标称值） | 1–2 天 | 单卡足够 |
| 6 | **PD 分离单机版** | 进程 A 只 prefill、进程 B 只 decode，量 KV 传输与配比 | 2–3 天 | 单机可验协议，收益要四机 |
| 7 | **重配置原子性 / 故障注入** | epoch 切换不丢请求、节点中途走掉仍能恢复（`TokenRecovery` 的跨节点路径现在语义不闭合） | 2–3 天 | 事件层面，单机可测 |
| 8 | **指标统一**（metrics/exporter） | 每段 compute/queue/hop/字节 + KV 字节 + 吞吐的自动出图 | 2 天 | 单机足够 |

**建议顺序：1 → 2 → 4 → 5**。
理由：#1 是纯测量，半天就能给出"批处理值不值得做"的判据；
#2 是 #1 的直接落点；#4 是弹性实验（我们的主线之一）的前置条件，且能暴露协议层问题；
#5 反过来提升 #2/#4 的价值（真实切换收益）。

## 4. 批处理要改什么（设计草案）

### 4.1 引擎侧（`hf_layered_engine.py`）

现状：`prefill(request_id, token_ids)` / `decode(request_id, token_id)`（`:312-336`），**一次一个请求**，
per-request 的 `past_key_values` 已经按 `(epoch, request_id)` 存在 `self._caches` 里（`:487-495`）。
**这个结构天然支持批处理**——每请求一份 cache，只要把 forward 的输入拼起来。

要加的东西：

| 项 | 说明 |
|---|---|
| `prefill_batch(reqs)` / `decode_batch(reqs)` | 一次 forward 处理 $K$ 个请求；每请求各自的 cache 通过 `past_key_values` 列表传入 |
| padding / position_ids / attention_mask | 变长序列必须处理。prefill 阶段各请求 token 数不同 → 要么右侧 pad + mask，要么用 varlen 接口 |
| 输出拆分 | 返回 `{request_id: hidden}`，末段返回每请求各自的 token |
| 批内 epoch 一致性 | **不允许跨 epoch 混批**：`self._caches` 的 key 带 epoch，混批会串线（现在靠 `generate` 开头的 epoch 校验挡住） |
| 显存核算 | KV 随 $K$ 线性增长；$K$ 的上界由 `memory_free` 决定，需要一个准入检查 |

### 4.2 数据面协议（`ActivationEnvelope`）

现在一个 envelope = 一个请求的一段 hidden（`types.py:131-203`，带 epoch + 校验和）。
批处理有两种做法：

- **A. 一个 envelope 装一批**（`payload` 内再分片，metadata 里带 request_id 列表）：省掉 $K-1$ 次 TCP 往返，
  但改动大、校验和语义要重新定义；
- **B. 每请求一个 envelope，但一次发送多个**（连接复用 + 批量 flush）：协议不动，
  只能省掉往返延迟，省不掉序列化开销。

**建议先 B 后 A**：B 能把 §2.1 里 hop 的"网络部分"（本来就只有 0.14 ms）压掉，
但真正的开销是序列化——那要靠 A。而 A 会牵动 `ActivationEnvelope` 的校验和与 epoch 语义，
是本项里**唯一有设计风险的地方**。

### 4.3 控制器侧（`task_scheduler.py` / `pipeline_controller.py`）

需要一个**攒批调度器**：每段维护待处理队列，按 `max_batch_size` / `max_wait_ms` / `max_batch_tokens`
三个闸门决定何时发一批。要注意：

- 攒批会**增加单请求延迟**（等待窗口），所以验收口径必须同时看两个量：
  固定 KV 预算下的 **tok/s vs $K$**，以及**单请求延迟不劣化超过 X%**；
- 批处理与"最慢段决定吞吐"叠加：批处理后各段的 $t_i$ 变化不一样（末段有 lm_head，
  单请求时它最慢），**最慢段会换人**，切层需要重新优化——这正好是 #5 那张表要喂的数据。

### 4.4 验收怎么定（避免"看着快了"）

| 指标 | 口径 |
|---|---|
| 加速比 | 同一段、同一模型、同一 $K$ 个请求，$T(1)/T(K)$（**单进程、无流水线**，排除混叠因素） |
| 固定开销 | 由 $T(K)=c_0+c_1K$ 拟合出的 $c_0$（单位 ms） |
| 正确性 | 批处理输出 vs 逐请求输出，逐 token 比对（复用 `verify_equivalence.py` 的思路） |
| 延迟代价 | 单请求 TTFT/TPOT 相对基线不劣化 > 10% |
| 显存 | 每段 KV 字节随 $K$ 的增长斜率 |

## 5. 微批（流水线重叠）要改什么（比批处理小）

现状：调度器**已经能并发跑 $K$ 个请求**（`real_pipeline_conc.json` 就是这么做出来的），
但每个请求各走一遍 4 段，段之间靠 agent 的锁串行化——所以并发一高，`queue_ms` 就涨
（CPU 实测 K=4 时 n0 的 prefill 排队 **356.9 ms**）。

要改的只有一件事：**把"按请求串行"改成"按段排队 + 顺序推进"**——
每段一个队列，段 $i$ 完成一个微批就交给段 $i+1$，让 $S$ 段同时在途。
这是纯调度改动（不需要动引擎），但要处理：

- **同 epoch 约束**：不同 epoch 的请求不能在同一条流水线里混跑（`LayeredPipelinePlacement` 已按 epoch 绑任务，天然可用）；
- **公平性**：避免长请求垄断某段 → FIFO + 每请求预算；
- **和批处理的关系**：批处理提高"每次调用干多少活"，微批提高"段有多忙"。
  两者叠加后的吞吐上界是 $1/\max_i t_i^{(K_{\text{batch}})}$，其中 $t_i^{(K)}$ 是批大小为 $K$ 时该段的耗时。

## 6. 明确不做的事（防止范围蔓延）

- **不在单机上做 TP**：实测每 token 需 ~56 次串行同步、跨 WiFi 单 token ~280 ms，单机做也证明不了跨机可行性；
- **不在单机上追四机吞吐结论**：四个 agent 共用一块 GPU（§2.4），单机吞吐数字只能当"机制验证"；
- **不改 `vllm/`、`LMCache/`**：它们不被本仓库管理（见 `.gitignore` 的说明），要用就以库/服务方式引用；
- **不在批处理里换 attention 实现**：先把"摊薄固定开销"这件事做干净，
  变长批的 varlen attention 等属于算子层，等批处理原型的瓶颈明确后再说。

## 7. 下一步的最小动作（如果只做一件事）

**做 §3 的 #1：单进程、单段、GPU 上的 $T(K)$ 曲线。**

它不需要写批处理代码，只要在一个 stage 引擎上循环 $K=1,2,4,8,16$，
记录每档的总耗时与每 token 耗时，拟合 $T(K)=c_0+c_1K$。产出三个数：

1. $c_0$：批处理能摊薄掉的那部分（现在看是 5–12 ms/次/段）；
2. $c_1$：真正随 token 增长的成本；
3. 拐点 $K^*$：$\frac{c_0}{K}$ 与 $c_1$ 可比的批大小——超过 $K^*$ 再加批就不划算了。

有了这三个数，"批处理值不值得做、做到多大"就从判断变成算术。
