# 弹性（R2）的代价与收益：值不值得做，怎么做最便宜

> 这份文档回答四个问题：
> **(1) 现成引擎的缺口到底是"不能运行时改切分"还是"在途请求会丢"？**——是两件事，别混。
> **(2) 节点离开时，做恢复的代价是否小于直接丢弃？**——给量化框架与数字。
> **(3) 恢复的收益到底有多大？如果很小，是不是不该做？**
> **(4) 如果加入/离开不频繁，能不能就用"停—重组—重启"这种最保守的方式？**——能，而且这是推荐的第一步。
>
> ⚠️ **数字口径**：本文的绝对秒数是**用实测的每层常数外推**得到（见
> `single-machine-scope-and-batching.md` §3.4），不是端到端实测。标注为"估算"。
> 每层每 token 边际 0.0217 ms、每层每次调用固定 2.55 ms（7B，RTX 4060 Laptop 实测）。

---

## 0. 结论先行

| 问题 | 答案 |
|---|---|
| 缺口是 R1 还是 R2？ | **两个都缺，但是两件事**。R1＝运行期改切分（所有引擎都定死在启动期）；R2＝在途请求不丢（与切分是否可变无关） |
| 恢复划算吗？ | **划算，但要选对方式**。最便宜的恢复＝**把已生成的 token 拼回 prompt，重放一次 prefill** |
| 便宜到什么程度？ | 恢复的代价 ≈ **重做一次 prefill**；丢弃的代价 ≈ **重做一次 prefill + 重做全部生成**。差的就是 decode 那一段 |
| 需要实现 KV 导出/导入吗？ | **不需要**（那是优化项）。重放路线不需要离开的机器配合、不需要冗余、不需要新接口 |
| 收益大吗？ | **取决于负载画像与 churn 频率**。长输出场景（Mooncake g=182、Codex g=520）收益大；短输出（Azure code g=13）收益小 |
| 不频繁时能保守处理吗？ | **能，且推荐**：档0"停—重组—重启"就是 vLLM 式语义，不需要任何恢复机制 |
| 那第一优先该优化什么？ | **不是恢复，而是重配置的装载时间**——7B 每段 35–126 s（实测外推），那是每次节点变化都必付的 |

## 1. 先把两个缺口分开：R1 ≠ R2

| | **R1：运行期改变层切分** | **R2：在途请求不丢** |
|---|---|---|
| 是什么 | 节点集合变了，重新决定"谁装哪几层" | 正在生成到一半的请求，不从头再来 |
| 现成引擎 | ❌ 全部定死在启动/配置期（llama.cpp 在 `llm_load_tensors`；vLLM/SGLang 靠启动参数；exo 能重放但**破坏性**：删实例、取消任务） | ❌ 消费级多机上是空白（见 `inference-engine-selection.md` §0.1） |
| 两者关系 | **可以分别获得**：①"能重切但丢请求"＝今天所有引擎；②"不重切但保住请求"＝把离开那台的层直接交给一台等价机器（热备）；③两者都要＝我们的目标 |

**为什么要分开**：因为它们的成本结构完全不同。

- R1 的成本是**装载**（把权重读进来、上卡）——我们实测 7B 每 4 层 **35.7 s**，
  按 12/4/4/8 切分最重的段0（6.7 GB）**≈126 s**（估算）。
- R2 的成本是**状态重建**（把"已经算到哪"这件事恢复回去）——见 §3，**1–5 s 级**。

**所以：R1 是大头，R2 是小头。** 这一点决定了优化的优先级（§6）。

## 2. 四个选项：节点离开时能做什么

场景：4 段流水线 A(0-11) / B(12-15) / C(16-19) / D(20-27)，**C 的机器离开了**，
此刻有 K 个请求在途（每个都生成到第 g 个 token，prompt 长 P）。

| 选项 | 做什么 | 请求要不要重来 | 走的代码路径 |
|---|---|---|---|
| **① 丢弃** | 幸存者重组流水线，被中断的请求作废，客户端重试 | **要**（用户重来一次） | 什么都不用做 |
| **② 重放（推荐）** | 重组后，把每个中断请求的"[原 prompt + 已生成的 g 个 token]"当成**新 prompt**，重放一次 prefill，然后继续生成 | 不要 | **复用现有 prefill 路径**（几乎零新代码） |
| **③ 搬 KV** | 优雅退出时把 C 那 4 层的 KV 导出，重组后装回去 | 不要 | 需要 KV 导出/导入（我们缺的那座桥） |
| **④ 冗余镜像** | 平时就把 C 的 KV 持续复制到 B/D，C 走了直接用副本 | 不要 | 还需要复制通道 + 一致性 |

**关键：②不需要任何新机制。** 把已生成 token 拼回 prompt 这件事，我在
`parameter-and-kv-management-status.md` §2 里指出"控制器从没做过"——现在可以看出，
**做那件小事本身就是一条可用的恢复路径**。

⚠️ 一个必须说清的边界：**重放要求采样可复现**。
贪心解码下确定性；采样解码下续出来的 token 会与"没中断的世界"略有不同（但仍是合法输出）。
另一种细微差异来自切分变化导致的不同 kernel/分块，数值会有极小差别。这两点都要在实验里声明。

## 3. 代价对比（估算，7B，用实测每层常数）

模型：生成 1 个 token ≈ 28 层 × (2.55 ms 固定 + 0.0217 ms) ≈ **72 ms**；
prefill 一个 token ≈ 28 层 × 0.0217 ms = **0.61 ms**（固定开销只在每次调用付一次）。

### 3.1 三种真实负载画像

| 画像 | P（prompt） | g（已生成） | 来源 |
|---|---|---|---|
| Azure code | 1500 | 13 | Azure LLM 2024 中位数 |
| Azure conversation | 1020 | 129 | 同上 |
| Mooncake | 7590 | 182 | Mooncake FAST'25 平均 |
| Codex agentic | 68329 | 520 | Codex/SWE-bench Pro 平均 |

### 3.2 单个被中断请求的代价

| 画像 | ① 丢弃：重做 prefill + 重做 g 个 token | ② 重放：只重做一次 prefill（P+g 个 token） | ③ 搬 KV：只搬 C 的 4 层 | **②比①省** |
|---|---|---|---|---|
| Azure code (P=1500, g=13) | 0.91 + 0.94 = **1.85 s** | 0.99 s | 12.4 MB → 0.3 s @40MB/s | 1.9× |
| Azure conv (P=1020, g=129) | 0.62 + 9.29 = **9.91 s** | **0.77 s** | 9.4 MB → 0.2 s | **12.9×** |
| Mooncake (P=7590, g=182) | 4.61 + 13.10 = **17.7 s** | **4.79 s** | 63.7 MB → 1.6 s | 3.7× |
| Codex agentic (P=68329, g=520) | 41.5 + 37.4 = **79.0 s** | **41.9 s** | 564 MB → 14.1 s | 1.9× |

读法：
- **重放省下的正是"重新生成"那一段**（g 次 decode）。所以**输出越长，重放越划算**（Azure conv 省 15×）。
- **搬 KV 只在"优雅退出"时可用**（机器被抱走时 KV 就已丢失），但它的量级很小——
  因为**只需搬离开那一段的层**：`2048 B/层/token × 4 层 × (P+g)`。
  这比我早先算的"整模型 KV"小 7 倍（前者误按 28 层算）。
- Codex 画像下 P 极大（68K），三种方式的绝对代价都很大，重放省得相对少——**说明"长 prompt"场景下，
  前缀缓存（把 prompt 的 KV 留在别处）比"救援在途请求"更值钱**。

### 3.3 全局：一次节点离开的总代价

**关键：一次节点离开会中断 K 个在途请求**（不是 1 个）——因为流水线断了，A 的输出没人接、C 在等 B 的输入，
所有在途请求都会卡住（只有"当前 token 已算完、能推到下一段"的能多走一步）。

| 项 | 代价 | 每次离开都要付吗 |
|---|---|---|
| **重配置装载**（R1） | 7B 每段 35–126 s（估算） | ✅ **必付** |
| 状态重建（R2） | ② 每请求 0.7–42 s，×K | 只在决定不丢弃时付 |
| 丢弃请求的用户代价 | 客户端重试、延迟预算归零 | 只在选择①时付 |

以 K=4、Azure conv 画像为例：丢弃白扔 ≈ 4 × 9.91 = **39.6 s 的 GPU 时间**；重放 ≈ 4 × 0.77 = **3.1 s**，
而且**可以与 126 s 的装载并行重放**（装载在前、重放在后，后者在关键路径上多花 ~3 s）。
→ **在 126 s 的重配置面前，多花 3 s 把 4 个请求救回来，几乎总是值得的。**

## 4. 收益有多少？怎么评估

收益 = **避免的浪费** × **中断请求数 K** × **离开频率**。三个因子都能量化，但第三个**没有公开数据**。

| 因子 | 怎么得到 | 状态 |
|---|---|---|
| 避免的浪费 | 上表（用 P、g 与实测每层常数算） | ✅ 可离线算，不需要 GPU |
| K（在途请求数） | 由并发策略决定；也是"一次离开影响多少用户" | ✅ 可测 |
| **离开频率** | **公开数据里没有**（我们已确认节点 churn 无公开数据集） | ❌ **只能作为我们实验的自变量并声明假设** |

**所以评估方式不是"算一个数"，而是画一条曲线**：

> 横轴 = 节点离开频率（例如 0.1 / 1 / 10 次每小时）、负载画像、K；
> 纵轴 = 吞吐（tok/s）、被丢弃请求比例、p99 延迟、以及"每次离开的额外等待"。
> 三种策略（①/②/③）各画一条。

**诚实的预期**：
- **低 churn（每小时 <1 次）**：节省的绝对 GPU 时间是"几十秒/小时"，对吞吐影响 <1% ——
  **从 GPU 利用率角度看，收益很小，不值得投入大工程**。
- **但收益还有非 GPU 的一面**：丢弃＝用户白等一整个请求（延迟预算归零）；
  在交互式场景里这是体验灾难，且会让 p99 延迟出现"整请求级"的尖峰。
  **这一面用 p99 / 丢弃率衡量，而不是用吞吐**——所以"收益小"只在吞吐口径下成立。
- **高 churn（无人机、抢占式实例）**：①完全不可用，必须②/③甚至④。

**结论**：R2 的收益**在吞吐口径下确实不大，但在"不丢请求"这个服务质量口径下很值钱**；
而由于最便宜的实现（②重放）几乎不需要新机制，**建议做②、不做④**。

## 5. 分档设计（对应"如果加入/离开不频繁"）

你的判断是对的：**不频繁时用"停—重组—重启"就够了**。把它写成分档：

| 档 | 机制 | 在途请求 | 需要什么新能力 | 适用频率 |
|---|---|---|---|---|
| **档0** | 停止接纳新请求 → 让能推进的请求推到断点 → 幸存者重组（重切 + 装载）→ 恢复服务 | **丢弃**（客户端重试） | **无**（我们已经能重切 + drain + 换 epoch） | 低（每小时 <1 次） |
| **档1** | 档0 + **重放恢复**：把"[prompt + 已生成 token]"当新 prompt 再 prefill 一遍，然后继续 | **保住** | 控制器记下已生成 token（拼回 prompt）——**半天级** | 低~中 |
| **档1b** | 档1 + 优雅退出时**导出 C 的 KV**（几十 MB），重组后装回 | 保住 | KV 导出/导入（2–3 天） | 中 |
| **档2** | KV 持续**镜像**到邻居，被抱走也能秒级恢复 | 保住 | 复制通道 + 一致性（等于每段 ≥2 持有者） | 高（无人机/抢占式） |

**建议：实现档0 + 档1，不做档2。** 理由：档0 已经能"活着"；档1 的增量成本极小（半年级接线），
收益是"用户不用重来"；档1b/档2 的复杂度陡增而收益只在极端频率下才显现。

**你的"最理想情况"（找台 c' 直接接手）**：需要一个与 C 等价且已预热的热备机——**这要求冗余**。
4 台机器里空一台出来，3 台要装下 4 台的量 → 装不下。所以"不动流水线其他部分"＝**用机器换时间**。
唯一便宜的近似是**把 C 的层就近分给 B 和 D**（只动两台、不新增机器），但 B/D 必须重新装载（几十秒）。

## 6. 那第一优先该优化什么：**不是恢复，是重配置**

因为 **R1 的装载代价（35–126 s）每次节点变化都必付，而 R2 的重放只有 1–5 s**。

优化装载的三条路（都能实测）：

| 方向 | 预期 | 怎么验 |
|---|---|---|
| **权重放 ext4 或加热缓存** | 实测 `/mnt/d` 冷读 112.7 MiB/s vs ext4 2319 MiB/s（20×） | 已有 `scripts/measure_fs_read.py` |
| **预转换单文件、按段打包** | 砍掉 dtype 转换那一段（实测 `prepare` 有效速率只有 ~53 MB/s，而读盘只占一半） | 计时分解 read / convert / upload |
| **蓝绿（先 prepare 再切流）** | 已经是这样；把 prepare 提前到"预测到要变"时 | 已有 `PipelineReconfigurationCoordinator` |

**并且要接受一个现实**：节点**突然**离开时没有可重叠的窗口——装载那几十秒无法隐藏。
所以真正压延迟的方向是**让这段装载本身变快**（小分片、低精度、预热缓存）。

## 7. 对"能不能复用 vLLM"的回答

**如果接受档0（重启式语义），vLLM 的功能是够的**——它就是"改配置重启、在途请求全丢、客户端重试"。
但有三条硬约束使它**不能直接替代**我们：

| vLLM 的约束 | 对我们的影响 |
|---|---|
| 官方要求各节点**执行环境完全一致**（原文 "to hide host heterogeneity"） | 8/6/4/4 异构直接冲突——它把异构当要藏的东西，我们当要利用的东西 |
| 切分是**配置期**定的 | 不等分能做（官方有 uneven splits），但**谁拿几层要人工算**；自动算 + 显存可行性校验是我们的贡献 |
| 无 drain / 无蓝绿 | 重启即在途全丢，且重启期间完全不可用 |

**所以我建议的复用形态是"思想复用 + 基线复用"**：
- **思想**：档0 的"停—重组—重启"就是 vLLM 的重启语义，我们不需要发明新语义；
- **基线**：vLLM 作数据中心对照；llama.cpp RPC 作跨机对照；Ollama 作单机对照（见引擎选型文档 §5）；
- **我们的增量**：① 自动算异构切分并校验显存；② epoch 蓝绿 + drain（重配置不打断在途）；③ 档1 重放恢复。
